复现失败排查表

复现失败时不要只看最后一行报错，要沿着模型、processor、动作解码、反归一化、性能和报告上下文逐层定位。

现象优先检查常见原因修复建议
模型加载失败checkpoint、trust_remote_code、Transformers 版本权重不完整、版本不匹配固定 revision，记录依赖版本
processor 加载失败processor config、tokenizer 文件本地目录缺文件重新下载并校验文件列表
动作维度不对ActionTokenizer、predict_action 输出手写解码或 API 不一致使用官方 predict_action 或 ActionTokenizer
动作范围异常unnorm_key、action stats训练/推理数据集统计不一致核对 dataset stats 和动作空间
延迟异常高dtype、device、量化是否生效模型在 CPU、KV cache/量化未启用打印 device map，分段 profiling
成功率低prompt、数据 split、环境随机性评估协议不一致或任务分布偏移固定 seed，保存失败视频和动作轨迹
报告数字复现不了config hash、checkpoint、seed实验上下文缺失强制输出 experiment_context

不要在验证脚本里手写 token_id - 32000。如果必须拆 generate 输出，也要调用当前仓库的 ActionTokenizer。

脚本安全执行口径

环境搭建脚本可以讲流程，但真实复现工程要避免把用户输入拼成 shell 命令。外部命令应记录 stdout、stderr、返回码和耗时，失败时给出可操作错误。

工程要求

命令形式优先使用参数列表，例如 ["conda", "env", "create", "-f", env_file]
输入安全不要把用户输入直接拼进 shell 命令
日志记录记录 stdout、stderr、returncode、duration
失败处理输出可操作错误，不只打印异常
下载追踪记录 URL、revision、hash 或依赖版本号

安全封装示例

def run_command(args, cwd=None, timeout=None):
    import subprocess
    import time

    start = time.time()
    result = subprocess.run(
        args,
        cwd=cwd,
        timeout=timeout,
        text=True,
        capture_output=True,
        check=False,
    )
    duration = time.time() - start

    record = {
        "cmd": args,
        "cwd": str(cwd) if cwd else None,
        "returncode": result.returncode,
        "stdout": result.stdout[-4000:],
        "stderr": result.stderr[-4000:],
        "duration_sec": duration,
    }

    if result.returncode != 0:
        raise RuntimeError(
            f"命令执行失败: {args}\n{result.stderr[-1000:]}"
        )

    return record

架构线

视觉编码器、projector、LLM、ActionTokenizer、动作反归一化。

工程线

环境复现、验证脚本、profiling、量化、LoRA、失败 case。

项目讲述模板：2分钟、5分钟、深挖版

面试讲项目时，不要只说“我跑通了模型”。要讲清背景、架构、复现、评估、优化、工程质量和局限性。

开场概述：我做的是 OpenVLA 的复现和工程分析项目。项目从模型加载、单图推理、动作解码、延迟 profiling 到量化和 LoRA 微调评估形成完整闭环。交付物包括可复现环境、验证脚本、评估报告、失败案例分析和面试材料。关键收获是：VLA 不能只看能否生成动作，还要看动作反归一化、闭环成功率、p99 延迟、gripper 错误和失败类型。报告中每个数字都记录 checkpoint、硬件、dtype、数据集 split、prompt 模板和 unnorm_key，保证结果可复查。
讲述段落应覆盖的重点
背景OpenVLA 把视觉、语言和动作统一到 VLM/VLA 框架中，适合机器人指令跟随。
架构视觉编码器提取图像特征，projector 对齐到 LLM 空间，LLM 生成 action tokens，ActionTokenizer 解码并反归一化为连续动作。
复现搭建环境、加载 checkpoint、跑单图推理、验证动作维度和范围，记录 latency 和显存。
评估不仅看离线 action error，也看 SimplerEnv/真机的闭环 success rate 和 failure type。
优化量化用于降低显存和延迟，但必须验证动作质量；LoRA 用于新任务适配，但要防止 loss 下降而成功率不升。
工程质量提供 README、配置文件、验证脚本、报告模板、失败案例和测试。
局限性模型延迟、显存、分布偏移、可解释性和动作精度仍是部署风险。
追问方向回答抓手
为什么不用手写 action token offset？OpenVLA 的动作 token 依赖官方 ActionTokenizer 和词表尾部 bin 设计，硬编码 offset 容易随版本失效。
为什么 loss 下降但成功率不升？label mask、action stats、unnorm_key、prompt 模板、gripper、闭环误差累积都可能导致离线/在线不一致。
量化怎么判断能不能上线？比较 BF16、INT8、NF4 的 success rate、action MAE、gripper error、latency p99、failure type。
如何保证复现可信？固定 checkpoint、环境、seed、数据 split，输出 validation_report 和 config hash。
失败 case 怎么分析？保存视频、动作轨迹、延迟日志、prompt 和状态，按视觉、动作、规划、控制、系统分类。

面试问答：D112 高频问题

1. 如何证明你真的复现了 OpenVLA？
给出环境文件、checkpoint、验证脚本、单图推理结果、动作维度检查、延迟/显存记录和评估报告；同时说明数据集 split、硬件、dtype、prompt 和 unnorm_key。
2. 报告里最容易被质疑的是什么？
没有上下文的数字。成功率、延迟、显存和量化收益必须能追溯到模型版本、数据集、硬件、评估协议和随机种子。
3. 如何展示项目深度？
不仅说模型能跑，还要讲清架构、数据流、推理瓶颈、量化和微调取舍、失败归因，以及你如何用实验验证每个判断。
