准确口径：动作 token 默认共享 tokenizer 词表最后 256 个 bin token；主推理接口优先用 `predict_action`，不要手写 `token_id - 32000`。

官方口径：主入口和内部拆解要分清

稳定主路径

正式推理、评估和部署时，把 model.predict_action(...) 当作主入口。它会处理生成、action token 解码和按 unnorm_key 反归一化，减少手写 offset 或漏掉动作统计的风险。

with torch.no_grad():

        **inputs,

        do_sample=False,
    )

源码级拆解

model.vision_backbone、model.projector、model.llm_backbone 适合讲解和 profiler，但它们属于内部结构，分支版本可能变化。拆 generate() 时也应调用官方 ActionTokenizer 解码逻辑。

Processor 主要处理图像和文本输入；动作离散化/反归一化更准确地说属于模型内部 ActionTokenizer 或 predict_action 路径，不应简单说成 AutoProcessor 的公开职责。

单图推理：主路径用 predict_action

日常评估和部署不要手写 action token 解码。使用官方/模型提供的 `predict_action`，让模型内部处理生成、动作 token 解码和反归一化。

image = Image.open("test_image.jpg").convert("RGB")
prompt = "In: What action should the robot take to pick up the red cup?\nOut:"
inputs = processor(prompt, image).to("cuda", dtype=torch.bfloat16)

with torch.no_grad():
    action = model.predict_action(
        **inputs,
        unnorm_key="bridge_orig",
        do_sample=False,
    )

print(action)  # [dx, dy, dz, droll, dpitch, dyaw, gripper]
什么时候拆 `generate()`？只有在 profiling、研究 action token 分布、debug logits 或验证 tokenizer 时才拆。拆开以后也要用官方 `decode_token_ids_to_actions()`，不要写死 offset。

速度分解：OpenVLA 慢在哪里

推理延迟通常由视觉编码、projection、LLM prefill、LLM decode、动作解码组成。对 VLA 来说，最常见瓶颈是 LLM 自回归 decode 7 个动作 token。

阶段测什么常见瓶颈优化方向
Processor图像 resize、tokenizeCPU 预处理慢缓存、并行、减少重复转换
Vision视觉编码器 forward高分辨率、多编码器降低分辨率、缓存视觉特征、轻量 backbone
Prefill输入上下文一次性计算prompt 太长、visual tokens 多截断 prompt、减少 visual tokens
Decode7 个动作 token 自回归生成LLM 解码串行量化、KV cache、TensorRT、减少动作 token

计时方法：墙钟时间和 CUDA 时间

CUDA 默认异步执行，直接用 time.perf_counter() 包住 GPU forward 可能低估真实耗时。端到端控制频率看墙钟时间，模块级 GPU profiling 更推荐 torch.cuda.Event。

端到端墙钟时间

torch.cuda.synchronize()
t0 = time.perf_counter()
action = model.predict_action(**inputs, unnorm_key="bridge_orig")
torch.cuda.synchronize()
latency_ms = (time.perf_counter() - t0) * 1000

适合回答“机器人每步到底要等多久”。要把相机采集、预处理、模型推理、env.step 或控制发送分开记录。

CUDA Event 分段时间

start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
with torch.no_grad():

end.record()
torch.cuda.synchronize()
decode_ms = start.elapsed_time(end)

量化对比：不能只看速度

模式显存速度风险建议
BF16高中等成本高基准结果、质量评估
INT8中可能更快少量精度损失优先尝试的部署优化
INT4低可能最快动作稳定性可能下降必须跑成功率和动作误差
VLA 的量化评估必须包含动作指标：平均动作差异、gripper 误差、成功率、失败模式分布。只报告 tokens/sec 不够。

量化前检查

基线先保存 BF16 latency、memory、success rate、动作轨迹。
任务集至少覆盖容易、困难、遮挡、长程、抓取失败高发任务。
日志记录模型 revision、torch/bnb 版本、GPU、batch、prompt。

量化后判断

动作差异逐维比较 mean_abs_diff、gripper 翻转率、动作饱和率。
闭环表现成功率、失败类型分布、p99 延迟必须同时看。
上线条件不能只因速度更快就上线，必须证明失败类型没有恶化。

离线评估

对已有数据比较 action error，便宜但不能验证闭环稳定性。

仿真评估

能看闭环成功率和失败视频，适合快速迭代。

真机评估

最终标准，但成本高、可重复性差，需要严格记录环境条件。

失败分类：不要把所有失败都叫模型不行

优先归因为视觉识别/定位问题：检查图像预处理、相机视角、遮挡、光照和目标是否出现在训练数据分布中。
失败类型现象常见原因改进方向
视觉误识别抓错对象遮挡、光照、目标太小数据增强、多视角、更强视觉编码器
动作计算错误方向/尺度不对`unnorm_key` 错、动作统计不匹配校准 action stats，检查反归一化
抓取失败碰到但夹不住抓取点、夹爪时机、接触动力学抓取数据增强、闭环纠偏、真机微调
长程失败前几步对，后面偏离误差累积、缺少高层规划分层策略、子目标、历史观测
系统延迟动作慢半拍LLM decode 慢、控制频率低量化、TensorRT、异步执行

归因流程：失败 case 怎么分析

证据链：失败归因要能复盘

看到失败视频后直接说“泛化不好”不够。一个可用的失败分析，需要把现象、日志、假设和消融实验连起来。

证据层记录内容判断问题
任务条件指令、物体、相机、光照、初始位姿是否集中在某类场景
视觉证据原图、裁剪、遮挡、目标位置、注意力/检测结果是否看错目标
动作证据7D action、动作差分、jerk、gripper 时机方向、尺度和平滑性是否异常
系统证据latency、Hz、显存、env step time是否闭环滞后
消融证据换视角、换 prompt、换 unnorm_key、加平滑哪个变量真正影响成功率

优化路线：根据瓶颈选择方案

目标优先方案代价验证方式
降低延迟INT8/INT4、KV cache、TensorRT可能影响动作质量延迟 + 成功率 + 动作误差
提升视觉鲁棒性图像增强、更多视角、改视觉编码器训练成本上升Variant success rate
提升抓取抓取失败数据、真机微调、闭环纠偏数据采集成本grasp success / contact video
提升长程任务分层规划、子目标、历史帧系统复杂度上升partial success 曲线

FAST / OFT：更贴近 VLA 的优化方向

FAST action tokenizer

通用量化主要降低模型计算成本，FAST 更聚焦动作表示本身。它的目标是用更高效的动作 tokenization 降低自回归动作生成负担，同时维持动作表达能力。

适用问题LLM decode 占比高、动作 token 生成拖慢控制频率。
验证方式每步延迟、动作平滑度、成功率、失败类型分布。

OFT / 任务微调

如果失败来自新任务、新机器人或数据分布差异，量化不会自动提高成功率。OFT/LoRA/任务数据微调应和推理优化分开评估。

适用问题新场景失败、目标物体分布变化、动作习惯不匹配。
验证方式held-out success rate、泛化任务、失败模式变化。
工程排序建议：先用 D109 的 profiler 和失败表定位问题，再决定是做量化/FAST 降延迟，还是做 OFT/LoRA 提升任务适配。不要把所有失败都交给同一种优化手段。

面试问答：D109 高频问题

1. 请描述 OpenVLA 推理完整流程。
图像和指令先进入 processor；视觉编码器提取 visual tokens；projector 对齐到 LLM hidden space；LLM 根据 visual tokens 和 text tokens 自回归生成动作 token；ActionTokenizer 解码为连续动作，并按 `unnorm_key` 反归一化到环境动作空间。
2. LLM decode 是主要瓶颈，怎么优化？
先确认 KV cache 和 profiler；再尝试 INT8/INT4、FlashAttention/TensorRT、缩短 prompt、减少 visual/action tokens、异步执行。每个优化都要同时报告延迟、显存、动作误差和成功率。
3. 成功率只有 60%，如何分析？
收集失败 episode 的视频、动作、状态、延迟；按视觉误识别、动作尺度错误、抓取失败、长程规划失败、系统延迟分类；和成功样本对比，提出假设并做消融。
