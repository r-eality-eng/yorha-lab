Model 精讲：PrismaticVLA 顶层 forward

`PrismaticVLA` 是 D107 的主入口。它的本质是把视觉 token 和文本 token 拼成 LLM 可接收的 embedding 序列，再让 LLM 预测动作 token。

def forward(images, input_ids, attention_mask, labels=None):
    visual_features = vision_backbone(images)       # [B, 729, 2176]
    visual_tokens = projector(visual_features)      # [B, 729, 4096]
    text_embeddings = llm.embed_tokens(input_ids)   # [B, T, 4096]
    inputs_embeds = concat(visual_tokens, text_embeddings, dim=1)
    full_mask = concat(ones_for_visual, attention_mask, dim=1)
    outputs = llm(inputs_embeds=inputs_embeds,
                  attention_mask=full_mask,
                  labels=labels)
    return outputs
步骤输入输出含义
视觉编码`[B,3,384,384]``[B,729,2176]`729 个 patch，每个 patch 融合语义和空间特征
投影`[B,729,2176]``[B,729,4096]`对齐 Llama2 hidden size
文本 embedding`[B,T]``[B,T,4096]`语言指令 token 化
拼接visual + text`[B,729+T,4096]`LLM 看到视觉上下文和指令
输出 logitsembedding 序列`[B,S,V]`只取动作位置计算 loss 或生成动作
最常见错误：把 `input_ids` 和 `inputs_embeds` 混用。视觉 token 没有词表 id，所以进入 LLM 时必须用 embedding 拼接，而不是把视觉特征硬塞成 token id。
第二个错误：拼接了 visual tokens 以后忘记同步扩展 `attention_mask`，会导致 LLM 对视觉 token 的注意力行为异常。

参数训练表：哪些模块冻结，哪些模块更新

读 OpenVLA 训练代码时，要先区分“参与 forward”和“参与训练”。视觉编码器参与 forward，但通常不参与反向更新；Projector 和 LLM 才是主要学习动作映射的地方。

模块参与 forward通常是否训练原因需要重点检查
SigLIP是冻结提供语义特征，节省显存，避免破坏预训练`requires_grad=False`，`eval()`，是否误开梯度
DINOv2是冻结提供空间/局部结构特征patch 数、输出层、图像尺寸
Projector是训练把视觉特征映射到 LLM hidden space输入维度、输出维度、初始化
Llama2是全参或 LoRA学习根据图像和指令生成动作 tokenLoRA target modules、bf16、checkpointing
ActionTokenizer训练外逻辑无参数连续动作和 token id 互转offset、bins、归一化范围、解码方向
代码阅读动作：打印 `sum(p.numel() for p in model.parameters() if p.requires_grad)`，再按模块打印可训练参数量。这个数字比阅读配置更可靠。
def count_trainable(module, name):
    total = sum(p.numel() for p in module.parameters())
    trainable = sum(p.numel() for p in module.parameters() if p.requires_grad)
    print(f"{name}: trainable={trainable/1e6:.1f}M / total={total/1e6:.1f}M")

视觉编码器：SigLIP + DINOv2 为什么要冻结

代码行为

视觉编码器通常设置 `requires_grad=False` 并在前向中使用 `torch.no_grad()`。这表示训练重点不在重新学习视觉基础能力，而在学习视觉到语言动作空间的对齐。

for p in siglip_encoder.parameters():
    p.requires_grad = False
for p in dinov2_encoder.parameters():
    p.requires_grad = False

with torch.no_grad():
    siglip_features = siglip_encoder(images)
    dinov2_features = dinov2_encoder(images)

工程原因

  • 节省视觉编码器反向传播的激活和优化器状态。
  • 避免机器人数据规模不足时破坏预训练视觉特征。
  • 把训练容量集中在 projector 和 LLM 的动作生成能力上。
  • 后续若要端到端微调，需要更小学习率、更大 batch 和更强正则。

Projector：视觉空间翻译成语言模型空间

Projector 不是可有可无的线性层。SigLIP、DINOv2、Llama2 来自不同训练目标，它们的特征空间不天然兼容。

projector = nn.Sequential(
    nn.Linear(2176, 4096),
    nn.GELU(),
    nn.Linear(4096, 4096),
)

Action Tokenizer：连续动作如何变成 LLM token

交互：量化精度计算

0.0078bin width
0.0039最大误差
256共享 bin token
7生成 token

编码和解码

# official idea: continuous action → shared action-bin token
bins = np.linspace(min_action, max_action, n_bins)
discretized_action = np.digitize(action, bins)
token_id = tokenizer.vocab_size - discretized_action

# decode: token id → continuous action
bin_index = tokenizer.vocab_size - token_id
bin_index = np.clip(bin_index - 1, 0, len(bin_centers) - 1)
action = bin_centers[bin_index]
讲解重点：官方 OpenVLA 默认让 7 个动作维度共享词表最后 256 个动作 bin token；维度由生成位置隐式区分。动作 token 化让机器人控制变成 next-token prediction，但也带来量化误差、自回归延迟和维度间相关性建模压力。
为什么动作 token 要放在词表末尾？

LLM 原始词表已经包含语言 token。OpenVLA 借用词表末尾的低频 token 作为动作 bin token，避免和常规语言 token 混淆。训练时模型在动作位置学习输出这些末尾 token，再由 ActionTokenizer 解码回连续动作。

为什么不是 `7 × 256 = 1792` 个动作 token？

官方实现更节省：7 个动作维度共享最后 256 个 bin token，第 1 个生成位置表示 Δx，第 2 个表示 Δy，依次到 gripper。这样动作词表不需要按维度复制，维度语义由序列位置承载。

项目容易误解的教学写法官方实现要点
动作词表`7 * 256 = 1792` 个 token默认共享最后 `256` 个动作 bin token
维度区分`dim_id * n_bins + bin_index`由 7 个生成位置隐式区分
编码方向`vocab_offset + bin_index``tokenizer.vocab_size - discretized_action`
解码手写固定 offset使用 `decode_token_ids_to_actions()`

Data Pipeline：OXE/RLDS 到 PyTorch Dataset

OpenVLA 的数据不是普通图片分类数据，而是机器人 trajectory。训练时通常把 episode 展开成 step，单个样本包含图像、语言指令和动作标签。

Episode

一次完整机器人执行轨迹，包含多个 step、metadata、终止标记等。

Step

一个时间步，包含 observation image、action、语言任务或相关状态。

Flat Index

为了随机训练，把 `(episode_idx, step_idx)` 展开成一维索引。

sample = {
    "image": image_tensor,          # [3, 384, 384]
    "instruction": "pick up the red cup",
    "action": action_tensor,        # [7], normalized to [-1, 1]
}
检查点：Data pipeline 最容易错在动作归一化、图像通道顺序、语言字段选择、episode 终止步是否参与训练。
易错点错误表现定位方法修复方向
动作统计量不匹配预测动作长期贴边，训练 loss 异常打印原始 action、normalized action、decoded action确认 dataset-specific min/max 或 mean/std
图像通道顺序错视觉特征异常，模型像看不到目标保存预处理前后图片，检查 RGB/BGR统一 PIL RGB 和 processor 预处理
语言字段取错模型无法区分任务，动作平均化打印每个 batch 的 instruction确认自然语言指令字段和 prompt 模板
终止步处理错训练到无意义动作或空动作检查 `is_terminal/is_last` 附近的 action过滤或单独处理终止 step

Collator：单样本如何拼成训练 batch

Dataset 返回的是单个样本，Collator 负责把一组样本变成模型可直接前向的 batch。它是 Data 和 Model 的接口。

字段来源输出形状用途
`pixel_values`图像 stack`[B,3,384,384]`送入视觉编码器
`input_ids`instruction prompt tokenize`[B,T]`文本输入
`attention_mask`tokenizer padding mask`[B,T]`控制 padding 不参与注意力
`labels`ActionTokenizer encode`[B,7]` 或序列 labels动作 token 监督
def collate(samples):
    pixel_values = torch.stack([s["image"] for s in samples])
    tokenized = tokenizer([build_prompt(s["instruction"]) for s in samples],
                          padding=True, return_tensors="pt")
    # 教学简化：官方通常会把 action token string 拼到序列里
    action_token_strings = [action_tokenizer(s["action"]) for s in samples]
    labels = build_action_labels(action_token_strings, tokenized)
    return {
        "pixel_values": pixel_values,
        "input_ids": tokenized.input_ids,
        "attention_mask": tokenized.attention_mask,
        "labels": labels,
    }
官方实现对照：这里的 `OpenVLACollator` 是教学抽象。官方更接近 `PaddedCollatorForActionPrediction`，动作编码通常通过 `ActionTokenizer.__call__()` 转成动作 token 字符串，再参与 tokenizer 和 causal LM label 构造。
教学名官方实现中更接近的组件作用
`OpenVLACollator``PaddedCollatorForActionPrediction`padding、attention mask、labels 整理
`OXEDataset``RLDSDataset` / `RLDSBatchTransform`RLDS 数据读取和样本转换
`ActionTokenizer.encode``ActionTokenizer.__call__`连续动作变为动作 token 字符串

完整数据流：从磁盘到 loss

Training 代码：Accelerate 把分布式细节包起来

训练脚本的骨架很标准：初始化 Accelerator，构建 model/dataset/optimizer/scheduler，调用 `accelerator.prepare()`，循环中 forward、backward、step。

accelerator = Accelerator(
    mixed_precision="bf16",
    gradient_accumulation_steps=config.gradient_accumulation,
)

model = build_openvla_model(config)
train_loader = DataLoader(dataset, collate_fn=collator, ...)
optimizer = torch.optim.AdamW(model.parameters(), lr=2e-5)
scheduler = get_cosine_schedule_with_warmup(optimizer, ...)

model, optimizer, train_loader, scheduler = accelerator.prepare(
    model, optimizer, train_loader, scheduler
)

for batch in train_loader:
    with accelerator.accumulate(model):
        outputs = model(**batch)
        loss = outputs.loss
        accelerator.backward(loss)
        accelerator.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        scheduler.step()
        optimizer.zero_grad()

BF16

减少显存并提升吞吐，比 FP16 更不容易数值溢出。

梯度累积

用多个 micro-batch 模拟更大的 global batch。

主进程日志

只在 `accelerator.is_main_process` 里写 wandb 或保存部分日志。

官方实现对照：上面的训练循环是为了讲清结构。官方微调入口更接近 `vla-scripts/finetune.py`，常见组合是 `torchrun`、DDP/PartialState、PEFT LoRA、`RLDSDataset`、`RLDSBatchTransform`、`PaddedCollatorForActionPrediction`。

训练循环逐行理解

代码动作实际含义如果出错会怎样
`with accelerator.accumulate(model)`控制梯度累积，多个 micro step 后再同步更新global batch 与预期不一致，学习率等效变化
`outputs = model(**batch)`完成视觉编码、token 拼接、LLM forward、loss 计算字段名或形状不对会直接报错
`accelerator.backward(loss)`兼容混合精度和分布式的反向传播直接 `loss.backward()` 可能破坏 Accelerate 封装
`clip_grad_norm_`限制梯度爆炸不开可能出现 NaN 或 loss 突然发散
`optimizer.step()`更新可训练参数若没有 trainable params，loss 不会有效下降
`scheduler.step()`更新学习率warmup 或 cosine 计划错会影响收敛

Loss 精讲：只在 Action Token 上算 CrossEntropy

OpenVLA 的训练目标不是让模型复述指令，而是根据图像和指令预测动作。因此视觉 token 和指令 token 通常不作为监督目标，核心监督在 7 个动作 token。

action_logits = logits[:, -7:, :]       # [B, 7, vocab_size]
loss = CrossEntropyLoss(
    action_logits.reshape(-1, vocab_size),
    action_labels.reshape(-1),
)
面试回答：动作离散化以后，本质就是 next-token prediction；差别在于 loss 的监督位置只对动作 token 生效，文本部分用于条件上下文。真实官方训练还要处理 causal LM 的 label shift，不能只机械理解成永远取 `logits[:, -7:, :]`。

显存优化：冻结视觉 + Gradient Checkpointing + LoRA

方法节省什么代价适用场景
冻结视觉编码器视觉模块梯度和优化器状态视觉适配能力下降默认训练和大多数微调
Gradient Checkpointing中间激活显存反向时重算，速度下降全参训练或长序列
LoRA可训练参数和优化器状态表达能力低于全参微调单卡或任务适配
INT8/INT4推理权重显存可能损失精度部署和快速验证
关键判断：如果目标是复现和学习，优先 LoRA 微调；如果目标是最高性能，需要全参训练或更复杂的分阶段解冻策略。

调试清单：代码读懂以后怎么排错

形状检查

  • `pixel_values` 是否 `[B,3,384,384]`。
  • `visual_tokens` 是否与 LLM hidden size 一致。
  • `attention_mask` 是否补上 visual token 部分。
  • `labels` 是否只覆盖 action token 位置。

数值检查

  • 图像是否按正确 mean/std 归一化。
  • 动作是否已经归一化到训练统计范围。
  • action token id 是否落在扩展词表范围。
  • loss 是否随训练下降，是否出现 NaN。
如果 loss 不下降，优先查什么？

先查 labels 是否对齐 action 位置，再查 ActionTokenizer 的 offset 和 bins，接着查图像预处理和 prompt 模板，最后再看学习率、batch size、LoRA target modules 等训练超参。

如果推理动作全是边界值，说明什么？

通常意味着动作归一化或解码范围有问题，也可能是模型没有正确生成动作词表范围内的 token。要打印原始 token id、bin index、连续动作值和训练数据 action stats。

面试问答：D107 高频问题

1. 请描述 OpenVLA 从原始数据到 loss 的完整训练链路。
OXE/RLDS 存储 episode 和 step；Dataset 展开 step，读取图像、指令和动作；图像 resize/normalize，动作归一化；Collator/BatchTransform 把动作转成词表末尾共享 bin token，并构造序列 labels；模型把图像转成 visual tokens，与 text embeddings 拼接进 Llama2；最后只在动作 token 对应位置计算 CrossEntropyLoss，并反向传播更新参数。
2. 为什么 forward 里要用 inputs_embeds，而不是只用 input_ids？
视觉特征不是语言词表里的离散 id，它已经是连续 embedding。要把 visual tokens 和 text embeddings 在 hidden dimension 上对齐后拼接，因此传给 LLM 的是 `inputs_embeds`。
3. Action Tokenizer 的主要优点和缺点是什么？
优点是可以复用 LLM 的 next-token prediction 框架，把动作预测变成分类问题；官方默认共享词表最后 256 个动作 bin token，7 维动作由生成位置区分。缺点是有量化误差、维度相关性依赖序列建模，并且自回归生成会增加控制延迟。
