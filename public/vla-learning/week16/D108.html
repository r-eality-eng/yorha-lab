BridgeData v2：训练数据从哪里来

BridgeData v2 是桌面机器人操作数据集，核心是 WidowX 机器人在桌面任务中的视觉观察、自然语言任务描述和低层动作。

数据粒度

一条 trajectory 是一次任务执行；trajectory 内部由多个 step 组成，每个 step 包含 observation、action、终止标志等。

任务类型

常见任务包括 pick、place、push、stack、open drawer 等，重点是桌面物体操作。

动作空间

通常讲成 7 维动作：`Δx, Δy, Δz, Δrx, Δry, Δrz, gripper`，训练前需要按数据统计量归一化。

字段典型形状含义常见错误
`observation.image``[H,W,3] uint8`第三人称相机图像RGB/BGR 搞反，resize 策略不一致
`observation.wrist_image``[H,W,3] uint8`腕部相机图像训练使用哪个视角不清楚
`action``[7] float32`末端增量和夹爪命令归一化统计量不匹配
`language_instruction`字符串自然语言任务指令prompt 模板与训练不一致

Trajectory / Step：RL 数据不是普通图片分类数据

关键区别：训练时经常随机采样单个 step，但任务语义来自整条 trajectory 的语言指令；不要把 episode、step、batch 这三层概念混在一起。

RLDS：为什么机器人数据喜欢 episode/step 格式

RLDS 可以理解为强化学习/机器人数据的标准化容器：外层是 dataset split，中间是 episodes，内层是 steps。它适合表达序列、终止标记、奖励、折扣、状态和动作。

tfds.Dataset
└── episode
    ├── episode_metadata
    └── steps
        ├── observation.image
        ├── observation.state
        ├── action
        ├── reward / discount
        ├── is_first
        ├── is_last / is_terminal
        └── language_instruction
格式优点缺点适用场景
RLDS / TFRecord统一 episode/step，适合 OXE 多机器人数据依赖 TensorFlow，PyTorch 接入有摩擦大规模机器人/RL 数据
HDF5随机访问方便，单文件层级清晰多进程读写和云存储场景要小心中等规模离线数据
NPZ / Pickle简单直观，上手快标准化差，不适合大规模混合数据小实验、临时调试
import tensorflow_datasets as tfds

ds = tfds.load("bridge", data_dir=data_dir, split="train")
for episode in ds.take(1):
    steps = episode["steps"]
    for step in steps.take(1):
        image = step["observation"]["image"].numpy()
        action = step["action"].numpy()
        instruction = step["language_instruction"].numpy().decode("utf-8")

Dataloader：把 episode 展平成可训练 step

训练需要随机 batch，而 RLDS 天然是 episode 序列。因此常见做法是构造 flat index：`dataset_idx / episode_idx / step_idx`，让 `__getitem__` 能随机返回一个 step 样本。

Flat Index 的价值

把不同长度的 episode 展开成统一的一维 step 列表，方便 shuffle、分布式采样和 batch 训练。

flat_index = [
  (episode_0, step_0),
  (episode_0, step_1),
  ...
  (episode_9, step_32),
]

PyTorch 接入点

`Dataset.__getitem__` 返回单样本；`BatchTransform/Collator` 负责把图像、指令、动作组装成模型输入。

sample = {
  "image": image_tensor,        # [3,H,W]
  "instruction": instruction,
  "action": normalized_action,  # [7]
}
工程风险：直接把所有 episode 预加载到内存会很重。真实训练通常更重视 streaming、interleave、prefetch、cache 和 worker 行为。

教学材料常用叫法OpenVLA 官方中更接近的组件说明

复现注意

  • 数据集 key/name 要和动作统计量一致，例如 `bridge_orig`。
  • BridgeData v2 数据很大，下载、解压和缓存都要提前规划磁盘。
  • `unnorm_key` 必须和训练/评估数据统计量匹配。

最小验证顺序

  1. 少量 episode 跑通 RLDS 读取。
  2. 打印 batch 的图像、prompt、labels。
  3. 跑一次 model forward。
  4. 再接 SimplerEnv 或 Bridge 评估。

图像预处理：RGB、尺寸、归一化必须和训练一致

检查项正确做法错误表现
RGB/BGR统一 PIL RGB 或官方 processor颜色异常，模型抓错物体
resize跟 backbone 配置一致，224/384 不要混用patch 数和视觉 token 对不上
归一化使用模型 processor 的 mean/std视觉特征分布偏移
视角明确 third-person 或 wrist camera训练和评估视角不一致

动作预处理：归一化、token 化、反归一化

动作预处理是 VLA 最容易出错的地方。训练时要把真实动作归一化并 token 化；推理时要把动作 token 解码并反归一化到环境需要的控制空间。

unnorm_key 很重要：同一个模型可能支持多个数据集/机器人动作统计量。推理评估时选错 `unnorm_key`，动作方向和尺度都会错，成功率会大幅下降。

DataLoader 性能：数据慢会让 GPU 空转

大规模 VLA 训练里，GPU 算力贵，但数据解码、图像 resize、TensorFlow 到 PyTorch 的转换都可能成为瓶颈。D108 需要建立一个判断：训练慢不一定是模型慢，也可能是 loader 慢。

优化点作用风险怎么验证
`num_workers`并行读取和预处理过大导致 CPU 抢占和内存暴涨看 GPU utilization 和 dataloader wait time
`pin_memory=True`加速 CPU→GPU 拷贝占用更多 pinned memory比较 batch transfer 时间
`persistent_workers=True`避免每个 epoch 重启 workerworker 内状态要小心看 epoch 边界是否卡顿
`prefetch`提前准备后续 batch内存压力增加比较 step time p50/p95
缓存 action stats避免重复扫描数据stats 和数据版本可能不一致记录 stats 文件 hash / 数据版本

SimplerEnv：为什么需要仿真评估

真机评估成本高、复现实验难。SimplerEnv 提供可重复的仿真任务，让 VLA 模型在视觉观察下闭环输出动作，并统计成功率。

输入

环境返回 observation，通常包含 RGB 图像、状态信息和任务相关 metadata。

策略

OpenVLA 根据图像和语言指令输出动作，执行在环境中。

输出

环境返回新 observation、reward、done、info，`info.success` 常用于成功率统计。

Visual Matching 和 Variant 有什么区别？

Visual Matching 更接近训练/真实基准视觉分布；Variant 改变颜色、位置、纹理或光照，用来测试泛化和鲁棒性。通常 Variant 更难。

结果表使用原则：SimplerEnv 成功率会随 checkpoint、模型版本、环境版本、任务协议和评估脚本变化。课件中的数字只能作为读表方式示意，不能脱离来源当成固定官方结论。

评估闭环：obs → predict_action → env.step

obs = env.reset()
for t in range(max_steps):
    image = Image.fromarray(obs["image"])
    inputs = processor(prompt, image).to(device, dtype=torch.bfloat16)

    with torch.no_grad():
        action = model.predict_action(
            **inputs,
            unnorm_key="bridge_orig",
            do_sample=False,
        )

    obs, reward, done, info = env.step(action)
    if done:
        break

success = info.get("success", False)
读评估代码时只抓三件事：输入图像是否和训练一致，动作是否正确反归一化，成功率是否按任务协议统计。

指标：成功率之外还要看什么

指标含义为什么重要
Success Rate任务最终是否完成最核心，便于横向比较
Partial Success是否完成中间阶段定位失败发生在哪一步
Episode Length完成任务用了多少步衡量效率和动作犹豫
Action Smoothness动作是否抖动判断策略是否稳定
Failure Category感知、语言、控制、环境失败帮助反推改进方向
常见失败：抓取点偏移、夹爪闭合时机错误、目标遮挡导致定位不稳定。

训练/评估一致性：成功率异常时先查这里

很多评估失败不是模型不会，而是训练和评估的输入输出协议不一致。下面这张表比单纯调学习率更重要。

一致性项训练侧评估侧不一致后果
图像尺寸processor/backbone 需要的尺寸环境 obs resize 到同一尺寸视觉 token 分布偏移
颜色空间RGBRGB，不要 BGR目标颜色语义错乱
prompt 模板`In: ...\nOut:`同一模板或官方模板语言上下文分布偏移
动作归一化按 dataset stats`unnorm_key` 对应同一 stats动作尺度和方向错误
gripper 约定开/合编码环境动作空间同一约定抓取时机和方向反了
最大步数训练轨迹长度分布评估 episode horizon成功率不可比
实用排查顺序：先录一段评估视频和动作日志，再检查图像、prompt、action、unnorm_key。只有这些都对了，再讨论模型结构或训练数据是否不足。

Domain Gap：BridgeData 和 SimplerEnv 为什么会不一致

视觉差异

光照、材质、相机位置、桌面纹理不同，会影响目标检测和空间定位。

动力学差异

仿真接触、摩擦、夹爪闭合和真实机器人不完全一致，动作可执行性会变。

任务定义差异

训练语言、评估任务名、成功判定可能不是一一对应。

差异类型观察现象改进方向
视觉 domain gap看得到但抓错对象图像增强、仿真随机化、多视角训练
动作 domain gap方向对但幅度不对重新校准 action stats / unnorm_key
接触动力学 gap碰到物体但无法稳定抓取更真实的仿真、真机微调、闭环纠偏
语言 gap任务理解偏差统一 prompt 模板和任务描述

常见 Bug 排查：从字段开始，不要先怪模型

数据侧

  • 图像通道顺序错误。
  • 使用了错误相机视角。
  • 语言指令字段为空或模板不一致。
  • episode 终止 step 被错误采样。

动作侧

  • 动作 min/max 统计量不匹配。
  • gripper 编码方向反了。
  • `unnorm_key` 选错。
  • token 解码和环境动作空间不一致。
现象优先检查定位方法
模型一直输出边界动作动作归一化/反归一化打印 raw、normalized、decoded action
抓取点总偏图像预处理和相机视角保存 processor 前后的图像
会动但不完成任务prompt 和任务定义打印每个 episode 的 instruction
SimplerEnv 成功率异常低动作尺度、环境任务名、成功判定录制视频并按失败类别标注

面试问答：D108 高频问题

1. 请描述 BridgeData 从磁盘到模型输入的完整数据流。
BridgeData 以 RLDS/TFRecord 存储 episode；tfds 读取后得到 episode/steps；Dataset 或 BatchTransform 从 step 中取 image、language instruction、action；图像 resize/normalize，动作按统计量归一化并转成词表末尾共享 bin token；Collator 形成 pixel_values、input_ids、attention_mask、labels，送入 OpenVLA 训练。
2. 为什么用 RLDS 而不是 HDF5？
RLDS 天然表达 episode/step/reward/action/terminal 等结构，适合多机器人 OXE 数据统一；它支持 tf.data 的并行读取和 prefetch。代价是依赖 TensorFlow，和 PyTorch 训练管线之间需要转换。
3. SimplerEnv 评估最容易错在哪里？
最容易错在动作反归一化和环境动作空间不匹配，其次是图像预处理、prompt 模板、任务名、成功判定和最大步数。评估失败时先看视频和动作日志，再判断是不是模型能力问题。
