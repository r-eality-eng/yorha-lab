设计空间：三类架构解决的问题不同

范式核心问题典型数据流最大取舍
HPT异构数据如何统一成可迁移表征多模态输入 → Stem → Trunk → Head推理快、迁移强，但动作生成多样性弱
RDT复杂连续动作分布如何高质量生成noisy action + condition + timestep → denoise质量高、多样性强，但采样延迟高
DiT Scaling扩散模型如何用 Transformer 规模化latent/action token + condition → DiT blocks容量和质量强，但训练与部署成本高

HPT：Stem-Trunk-Head 的统一表征路线

HPT 的强项是“统一输入和迁移”。如果数据来自不同机器人、不同传感器、不同任务，HPT-style 模块化表征通常更容易 debug 和上线。

RDT：把动作生成看成条件去噪

RDT 的代价主要在采样链路：多步去噪会带来延迟、显存和调参成本。真实部署时要关心采样步数、控制频率和失败恢复。

DiT Scaling：把扩散模型做成可扩展 Transformer

DiT 的核心

把扩散模型中的 U-Net 风格 backbone 换成 Transformer blocks，让模型容量、token 数、条件注入方式可以更规律地扩展。

机器人里的意义

动作序列、视觉 token、语言 token、本体状态都可以被组织成条件生成问题。DiT 提供的是“大规模条件去噪”的架构路线。

# 教学版 DiT 数据流
latent_action = action_encoder(noisy_action)      # [B, T, C]
condition = condition_encoder(image, text, state) # [B, L, C]
for block in dit_blocks:
    latent_action = block(latent_action, condition, timestep)
pred = output_head(latent_action)

混合架构：真实项目经常不是三选一

推荐工程路线：先用 HPT-style encoder 统一多模态表征，再根据动作复杂度和延迟约束选择 deterministic head、RDT head 或 DiT head。

面试表达：不要说“谁更好”，要说“约束下怎么选”

如果强调低延迟、多机器人迁移和工程可控性，我会优先 HPT；如果任务存在多条合理动作轨迹、复杂接触和高质量生成需求，我会优先 RDT。但 RDT 的多步采样要用少步采样、蒸馏或 receding horizon 控制延迟。

DiT Scaling 的意义是把扩散式动作生成放进 Transformer 扩展规律里。它适合大规模数据和算力，但不是免费午餐：训练成本、采样成本、条件注入稳定性都要评估。

实际项目可以用 HPT 做多模态和跨机器人表征，再挂一个 RDT/DiT action generator。这样 HPT 解决“看懂世界和迁移”，RDT/DiT 解决“复杂动作怎么生成”。

部署风险包括采样延迟超标、动作空间未对齐、条件被模型忽略、扩散随机性带来不稳定、离线指标和闭环成功率脱节，以及新机器人 adapter 迁移不足。

自测

1. HPT 最适合解决什么问题？
异构输入、多机器人、多任务的统一表征和迁移问题。它的优势是模块化、低延迟、debug 较容易。
2. RDT 为什么生成质量通常更强？
因为扩散模型通过条件去噪建模动作分布，天然适合多峰轨迹和复杂连续动作，但代价是多步采样。
3. 什么情况下应该考虑混合架构？
当项目同时需要跨机器人泛化、复杂动作质量和上线延迟控制时，可以用 HPT 统一表征，再接少步 RDT/DiT 或快速 head。

最终总结

D118 的一句话总结：HPT、RDT、DiT 不是简单排名关系，而是三种不同架构路线。HPT 解决统一表征和迁移，RDT 解决复杂动作分布生成，DiT 解决扩散 Transformer 的规模化。

默认工程路线

先用 HPT-style encoder 统一输入，再根据动作复杂度选择 deterministic/RDT/DiT head。

面试关键词

实时性、多样性、异构数据、采样步数、条件注入、动作空间对齐、闭环成功率。
