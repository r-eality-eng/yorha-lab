用 DCT 把连续动作变成高效动作 Token

这一天的重点不是背公式，而是理解：机器人动作轨迹通常是平滑信号，FAST-style tokenizer 利用低频结构，用更少 token 表示更长、更稳定的动作序列。

学习目标：今天要建立一条完整链路

目标

动作压缩

理解为什么把 `[T,D]` 动作序列直接逐维离散化会浪费 token。

方法

DCT 变换

把时间序列转到频域，优先保留低频系数，因为机器人动作通常连续且平滑。

接口

Tokenizer

完成 action → coefficient → token → coefficient → action 的闭环。

系统

π0-FAST

把动作 token 接入 VLA，让模型像生成文本 token 一样生成动作 token。

准确性口径：本页代码是教学版接口，用来讲清楚数据形状和设计逻辑；真实 FAST / FAST+ 还包含 tokenizer 训练、BPE/序列压缩、词表扩展、数据归一化和系统级优化。

为什么需要动作 Tokenization

VLA 模型最终要输出机器人动作。动作可以连续回归，也可以离散成 token。FAST 的动机是尽量同时拿到“连续动作的高保真”和“离散 token 的高生成效率”。

方案优点问题适合场景
Flow Matching 连续动作动作质量高，适合多峰分布和平滑控制采样可能需要多步，难以直接复用 LM token 生成范式高精度短 chunk 控制
256 bins 逐维离散简单、易接入语言模型、解码快token 数随 `T*D` 增长，容易丢失时序结构短序列、低维动作、快速 baseline

DCT 直觉：为什么低频能代表主要动作

机器人末端轨迹、关节角、夹爪开合通常不是随机抖动，而是有连续趋势的平滑信号。DCT 会把这种趋势集中到低频系数里，高频部分更多描述细小抖动或局部修正。

直觉上，低频回答“整体往哪走”，高频回答“局部怎么抖”。对于机器人控制，整体趋势通常比高频细节更重要。
# 正交 DCT-II 的教学实现
def dct_time(actions):
    # actions: [B, T, D]
    C = build_dct_matrix(T)      # [T, T]
    coeffs = torch.einsum("kt,btd->bkd", C, actions)
    return coeffs                # [B, T, D]

FAST Tokenizer 数据流

Token 数变少

逐维 bins 通常需要 `T*D` 个 token；低频 DCT 可以只用 `K` 个向量 token，或 `K*D` 个标量 token。

时序结构保留

DCT 先沿时间维建模整体轨迹，再量化频域结构，比逐时间步独立 bins 更懂“动作是一条轨迹”。

与 LM 对齐

核心实现：先把形状讲对

最容易出错的地方不是 DCT 公式，而是 token shape。下面采用“每个频率向量 `[D]` 对应一个 codebook id”的 VQ 口径。

class FASTTokenizerVQ(nn.Module):
    def tokenize(self, actions):
        # actions: [B, T, D]
        coeffs = DCTTransform.dct_time(actions)      # [B, T, D]
        low = coeffs[:, :K, :]                       # [B, K, D]
        quantized, token_flat, loss = vq(low.reshape(B*K, D))
        tokens = token_flat.reshape(B, K)            # [B, K]
        return tokens, quantized.reshape(B, K, D), loss

    def detokenize(self, tokens):
        # tokens: [B, K]
        quantized = codebook(tokens.reshape(-1)).reshape(B, K, D)
        full = zeros([B, T, D])
        full[:, :K, :] = quantized
        return DCTTransform.idct_time(full)
如果你希望 token 是 `[B,K,D]`，那是另一种设计：每个动作维度单独标量量化。两种都可以讲，但不能混在同一段代码里。

FAST vs 256 bins：不是简单谁更快

维度256 binsFAST / DCT Tokenizer
离散对象每个时间步、每个动作维度独立离散先编码整个时间序列，再量化低频系数
token 数`T*D` 线性增长`K` 或 `K*D`，通常 `K < T`
误差形态逐维量化误差，可能造成抖动频域截断误差，通常表现为更平滑
工程复杂度很低需要 DCT、量化、码本训练、反变换
系统收益适合 baseline自回归步数更少，KV cache 压力更低，长 chunk 更有优势
速度比较不能只测 tokenizer/detokenizer。真正重要的是端到端：VLA 生成多少动作 token、Transformer 解码多少步、KV cache 占多少、控制周期是否满足机器人实时性。

π0-FAST：动作 Token 如何接入 VLA

统一序列

视觉 token、文本 token、动作 token 可以进入同一个 Transformer 序列，但需要清晰的 modality embedding。

动作位置编码

动作 token 的位置最好编码频率 index、chunk index、甚至 embodiment，否则模型难以理解 token 的控制含义。

词表扩展

动作 token 可以作为额外词表，也可以用单独 action head；关键是训练损失和解码接口一致。

FAST Tokenizer 训练流程：从离线轨迹到动作词表

真实 FAST-style 系统不是手写一个 DCT 函数就结束。tokenizer 本身需要离线训练、验证、保存统计量，并和 VLA 的词表或 action head 对齐。

预处理

统一坐标系、动作尺度、chunk 长度和夹爪定义。不同机器人混训时，这一步决定码本是否能泛化。

码本学习

码本太小会过度平滑，码本太大会增加词表压力。训练时要同时看重建误差、码本使用率和稀有 token 比例。

接入策略

可以扩展统一词表，也可以用独立 action head。教学和工程排错阶段，独立 action head 通常更清晰。

def test_fast_tokenizer_shapes():
    tokenizer = FASTTokenizer(action_dim=7, chunk_size=16, num_freq_bins=8)
    actions = torch.randn(4, 16, 7)
    tokens, quantized, loss = tokenizer.tokenize(actions)
    assert tokens.shape == (4, 8)
    assert quantized.shape == (4, 8, 7)
    assert tokenizer.detokenize(tokens).shape == actions.shape

实现坑位：D117 最该补的地方

1. token shape 混乱

`[B,K]` 和 `[B,K,D]` 是两种不同设计。向量 VQ 是 `[B,K]`；逐维标量量化才是 `[B,K,D]`。

2. 层次化切片错误

频段 token 的切片长度由 `high-low` 决定，不由 `codebook_size` 决定。码本大小只影响 token 取值范围。

3. 部署版变量未定义

detokenize 不能引用不存在的 `actions`。应显式创建 `[B,T,D]` 的零张量，再写回重要维度。

4. 忽略归一化

不同机器人动作尺度差异很大。DCT 前后都应有 action normalization，否则码本会被尺度差异污染。

面试表达：把 FAST 讲成系统设计

DCT 适合动作 tokenization，是因为机器人动作在时间上通常平滑，低频系数能覆盖大部分轨迹能量。保留低频可以压缩 token，同时保持主要运动趋势；高频被截断后，误差通常表现为更平滑，而不是逐维随机抖动。

训练时先把目标动作通过 FAST tokenizer 转成动作 token，再让 VLA 根据图像和语言预测这些 token；推理时 VLA 自回归生成动作 token，再通过反量化和 IDCT 还原连续 action chunk。工程上要处理词表扩展、动作位置编码和 modality embedding。

不能只报告 tokenizer 局部速度和 MSE。应该同时报告重建质量、轨迹平滑性、端到端解码延迟、token 数、KV cache、真实任务成功率和跨机器人泛化表现。

主要风险是 tokenizer 复杂度上升、码本训练不稳定、动作尺度归一化不足、高频细节丢失，以及 token shape 或频段切片实现错误。系统上线前需要可逆性单测、边界动作测试和真实控制闭环评估。

自测：确认你真的理解 D117

1. 如果动作是 `[B,T,D]`，向量 VQ 对每个频率的 `[D]` 系数量化，token 形状应该是什么？
应该是 `[B,K]`。每个低频频率向量对应一个 codebook index。若是 `[B,K,D]`，那代表逐维标量量化，是另一种设计。
2. FAST 的速度收益主要来自 DCT 本身很快吗？
不主要是。收益更多来自动作 token 数减少，自回归解码步数变少，KV cache 压力降低，端到端生成链路更短。
3. 为什么不能只用 MSE 评价动作 tokenizer？
机器人控制还关心轨迹平滑性、终点误差、碰撞率、成功率和闭环稳定性。MSE 小不一定代表任务执行好。

最终总结

D117 的一句话总结：FAST / π0-FAST 把动作看成时间信号，先用 DCT 提取低频结构，再把频域系数量化为动作 token，从而让 VLA 用更少 token 生成更长、更平滑的 action chunk。

你要记住的本质

动作 tokenization 不是简单离散化，而是在压缩率、重建质量和生成效率之间做系统权衡。

你要警惕的问题

token shape、频段切片、归一化、码本训练和真实控制闭环，是最容易出错的工程点。
