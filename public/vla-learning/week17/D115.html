整体架构：从条件到连续动作序列

Toy 数据：condition 必须真的控制 action

D115 的原始目标是模拟 “VLM condition → action sequence”。因此 toy dataset 不能让 condition 和 action 完全独立。否则无论模型多强，都无法学到条件控制。

错误设计

condition = randn([N, C])
actions = randn([N, K, D])

# 问题：condition 与 action 无关
# 模型学不到 c -> action，只能学 action 边缘分布

更合理的 Toy 设计

condition = randn([N, C])
base = tanh(condition @ W)
mode = sign(condition[:, 0])
base[:, 0] += 0.4 * mode

actions[t] = 0.7 * actions[t-1] + noise
这样模型至少要学三件事：condition 到基础动作的映射、时间步之间的相关性、不同 mode 下的动作偏向。

Flow Matching 核心：训练学 forward velocity，推理反向积分

训练公式

a_t = (1 - t) * a_0 + t * ε

t = 0: clean action a_0
t = 1: noise ε

target_velocity = ε - a_0
loss = || vθ(a_t, t, c) - target_velocity ||²

推理伪代码

a_t = randn([B, K, D])
t = 1.0
dt = 1.0 / ode_steps

for step in range(ode_steps):
    v = model(a_t, t, condition)
    a_t = a_t - v * dt
    t = t - dt

actions = clip(a_t)
不要把 ε - a_0 说成“到达干净动作的方向”。在本页约定里它是 data → noise 的 forward 速度；推理要 noise → data，所以更新时减去速度。

交互：拖动 t，看训练和推理方向

Flow 时间步

aₜ
t=0 动作 a₀t=1 噪声 ε

当前解释

当前位置动作和噪声的中间状态
训练目标学习从左到右的 ε - a_0
推理方向从右到左，使用 a_t = a_t - v * dt

AR 对比：串行生成动作步

自回归动作生成把 action chunk 看成序列：先生成第 1 步，再用已生成的动作生成第 2 步。它的核心成本来自串行依赖。

维度Flow Matching Toy HeadAutoregressive Toy Head
输入condition + noisy action + tcondition + previous actions
输出整个 action chunk 的速度场逐步输出 action step
推理次数约等于 ODE steps约等于 horizon 或 action token 数
多样性来自初始噪声若是确定性回归则无多样性；若采样分布则可有多样性
风险ODE steps 太多会慢长序列误差累积和串行延迟

ODE Solver 对比：Euler 和 Midpoint 都要注意反向积分

本材料统一约定模型预测的是 data → noise 的 forward velocity。因此推理阶段从 noise → data 时，不管用 Euler 还是 midpoint，都要沿相反方向更新。

Euler 法

x = torch.randn(B, K, D, device=condition.device)
dt = 1.0 / num_steps
t = 1.0

for _ in range(num_steps):
    t_tensor = torch.full((B, 1), t, device=condition.device)
    v = model(x, t_tensor, condition)
    x = x - v * dt
    t -= dt

Midpoint 法

v_current = model(x, t_tensor, condition)
x_mid = x - 0.5 * dt * v_current

t_mid = t - 0.5 * dt
v_mid = model(x_mid, t_mid_tensor, condition)
x = x - dt * v_mid
Solver优点代价D115要点
Euler简单、快、最容易检查方向同样步数下误差可能更大适合 toy 实验和 sanity check
Midpoint比 Euler 更精确每一步通常多一次模型调用文字公式和代码都必须使用反向积分符号

面试表达：怎么讲 D115

我用一个 toy action generator 验证 π0 action head 的核心机制：给定 condition 和带噪 action，模型学习 Flow Matching 速度场；训练目标是 ε-a0，推理时从噪声开始反向积分得到连续 action chunk。
为什么要让 toy action 依赖 condition？否则模型学不到条件控制，只能拟合动作边缘分布。
为什么推理时减去 velocity？因为训练的 velocity 是 data → noise，推理要 noise → data。
为什么 FM 可以有多样性？同一 condition 下从不同初始噪声出发，可能流向不同合理动作。
为什么 toy 不能代表真实性能？缺少真实 VLM、真实动作统计、闭环控制、安全边界和真实环境评估。
我不会直接说 FM 一定比 AR 快。更严谨的说法是：FM 前向次数约等于 ODE steps，AR 前向次数约等于 action token 数。谁更快取决于 horizon、steps、模型大小、batch、缓存和硬件。

自测：确认你真的能写 D115

1. 为什么 toy dataset 里的 action 必须依赖 condition？
因为任务是学习 condition → action。如果二者独立，模型无法学条件控制，只能拟合动作边缘分布。
2. 本页约定下，FM 的训练 target 是什么？
target_velocity = noise - actions，也就是 data → noise 的 forward velocity。
3. 推理时为什么是 a_t = a_t - v * dt？
因为推理从噪声回到数据，方向与训练的 forward velocity 相反。
4. 为什么速度对比必须做 GPU 同步？
CUDA kernel 异步执行，如果不在计时前后同步，计时结果可能只测到调度时间，不是真实执行时间。
5. Toy 到真实 π0-style 系统最重要的替换是什么？
把随机 condition 替换为 VLM 中间层条件，把 MLP 替换为 Transformer Action Expert，并补齐真实动作归一化、安全限幅和闭环评估。

D115 最终总结

1. 实操核心

D115 把 π0 action head 抽象成 condition + noisy action + time → velocity field。

2. 方向统一

训练学 ε-a0，推理从噪声反向积分到动作。

3. Toy 数据要可学习

condition 必须控制 action，否则实验无法验证条件生成。

4. AR 对比要公平

比较 steps、horizon、模型大小、batch 和硬件，不下绝对结论。

5. 迁移到真实系统

需要 VLM condition、Transformer expert、动作归一化、安全控制和闭环评估。
